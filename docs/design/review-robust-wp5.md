## Checked, no finding

- **Take-back race with the pilot.** The pilot claims with `mv`, and WP5 takes back with `rm` (no `-f`). On one filesystem these are a server-side rename and unlink of the same name, so exactly one succeeds. If the `rm` loses, the step was claimed and fails as before. An ambiguous `rm` (-1, or an NFS retransmit that returns ENOENT) also returns `False`. Worst case is a lost step, never a step that runs twice.
- **Running in both allocations.** The old launcher is deleted before the new one is written. The old `run/<step>.job` is only data: the old pilot runs only `run/<step>.sh`, which never existed. `exit_code` stays in `job_dir`, and only the new launcher can write it. No duplicate, except for finding 3.
- **Cancel during and after the move.** Covered by the code and by tests. A signal while the handle is being updated goes to the new dir. The second signal after the move is harmless: its `rm` fails and `_announce` dedups.
- **Move cap.** `moves` is kept in `extra` as a string and checked before any command runs. `max_step_moves=0` turns the move off, and `le=10` bounds it.
- **Shared squeue cache.** `_requeue_step` does not touch the cache. `_allocation()` resets it when it submits. A read for an old id is never stored (`job_id == alloc.job_id`), so it cannot evict the new reading (probe for finding 8).
- **Job id file and record.** `_publish_job_id` writes the new id to the task's job-id file, so `SlurmJobScope` follows it. `_record.job_id` and `script_path` are updated, and the record gets a new SUBMITTED transition. `raw_job_id` equals `job_id`, as `launch` sets it for shared targets.
- **Quoting.** The old `rm` path and every path in the rebuilt launcher go through `shlex.quote`. The job id matches `_JOB_ID` in `_sbatch`. The step name comes from the job dir name and is quoted wherever it is used. No injection found.
